## 6. Hallazgo P0 — auth admin casera (SACRE-P0-1, confirmado VIGENTE)

Verificado hoy en código, solo lectura, sin modificar:

- `app/admin/login/page.tsx:21` — **credenciales hardcodeadas en el cliente**: `if (username === "sacre" && password === "chocolate")` — usuario y contraseña visibles en el bundle JS que baja cualquier visitante.
- `app/admin/login/page.tsx:23` — sesión: `localStorage.setItem("admin_session", "true")` — trivialmente forgeable desde la consola del navegador.
- `app/admin/layout.tsx:35` — única "protección" de la ruta: `useEffect` client-side que lee `localStorage.getItem("admin_session")` y redirige. **No hay middleware**: `ls middleware.ts src/middleware.ts` → no existe. Las páginas `/admin/pedidos`, `/admin/productos` y el dashboard son server-rendered y accesibles por URL directa sin ninguna verificación server-side.
- Sin Supabase Auth ni RLS aplicados: la migración `0001_init.sql` ya define RLS con 8 policies (products/orders/order_items/notifications/product_categories) diseñadas para admin autenticado, pero **no hay proyecto Supabase SACRE en la org** (P0-3 sigue abierto) — el DDL nunca se aplicó. Hoy el admin consume mocks de `lib/data.ts`.

**Clasificación: P0 — sigue abierto tal como lo dejó el barrido del 2026-09-16 (P0-1).** La autenticación es cosmética: cualquiera que lea el JS del sitio obtiene las credenciales y, peor, ni siquiera las necesita porque la sesión es un flag de localStorage sin validación del servidor. Remediación (cuando toque, con LGTM): Supabase Auth + middleware server-side + RLS — la base ya está escrita en la migración.
